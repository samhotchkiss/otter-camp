# Spec Issues

Issues found during spec review that must be resolved before building starts.
Each issue must be resolved by Sam before Codex picks up the affected task.

| # | Severity | Affected Docs | Issue | Status |
|---|----------|--------------|-------|--------|
| 1 | BLOCKER | 05, 14 | Doc 05 schema defines `budget_cap_cents` (integer, per-agent cost cap in cents) on the `agent` table. Doc 14 resolved question #24 explicitly states: "rename `budget_cap_cents` to `budget_cap_tokens`" and specifies that all three budget levels (org, project, agent) use tokens as the unit, with dollar estimates shown display-only in the UI. The doc 05 schema was not updated to reflect this resolution. The column name and type need to be decided and doc 05 updated before the agent table DDL can be finalized. | Open |
| 2 | AMBIGUOUS | 04, 14 | Doc 04 describes a 7-step bootstrap sequence (steps 1–7: migrations → org → first user → starter trio → provider connections → org session → audit event). Doc 14 resolved question #7 explicitly states "doc 04's bootstrap sequence is stale — doc 14's 10-step sequence is authoritative." The 10-step sequence in doc 14 adds: create org-level skills repo + default skills (step 4), seed model profiles (step 5), seed default flow templates (step 6) — all before seeding starter trio (step 7). Doc 04's text has not been updated to acknowledge this and still presents its own 7-step sequence as current. A developer reading doc 04 alone will implement the wrong sequence. Doc 04 should be updated to defer to doc 14 or include the correct 10-step sequence. | Open |
| 3 | GAP | 03 | `inbox_item.item_type` includes `'browser_handoff'` as a valid value in the schema check constraint in doc 03. However, neither doc 03 nor any of the other 6 docs read in this iteration define what a `browser_handoff` inbox item is, when it is created, what actions are available on it, or what its `action_payload` looks like. Likely defined in doc 11 (System Integration — CLI and Browser). Must be confirmed when doc 11 is read. If doc 11 does not define it, this is a gap that needs to be filled before `inbox_item` can be implemented. | Open |
| 4 | AMBIGUOUS | 05, 14 | Doc 05 states: "Private memory: Default for staff PMs, Frank, Lori, and Ellie: true. Default for all other staff and all temps: false." Doc 14 resolved question #8 addresses a prior inconsistency about Lori's private memory and confirms "doc 05 is authoritative — all staff agents (including Lori) have private memory enabled." The current doc 05 text already includes Lori in the true set, so these are consistent. However, the doc 14 bootstrap dataset section says under Lori: "Private memory: enabled (default for all staff — doc 05)" which appears to generalize to ALL staff, not just PMs, Frank, Lori, and Ellie. This wording conflicts with the doc 05 body text which explicitly limits private_memory=true to those four roles. Clarify whether all staff agents get private_memory=true or only the named four. | Open |
| 5 | AMBIGUOUS | 05 | The `agent.lifecycle_status` column combines staff and temp state machines into one column with values: draft, active, paused, retired, cancelled, expired, promoted. The check constraint allows all 7 values but the spec text says staff agents use draft/active/paused/retired/cancelled and temp agents use active/expired/promoted. There is no DB-level constraint preventing a staff agent from reaching 'expired' or a temp agent from reaching 'draft' — only application-layer enforcement is implied. This should either have a check constraint referencing `agent_class` or be explicitly acknowledged as application-layer-only enforcement to avoid ambiguity for implementers. | Open |
| 6 | GAP | 03 | The `flow_node` table references a `flow_node_skill` join table ("Skills are linked via flow_node_skill join table (see doc 10)") but this table is not defined in docs 01–05 or 14. It must be defined in doc 10 (Skills Integration). Flag for confirmation when reading doc 10. If doc 10 does not define the `flow_node_skill` table with columns, this is a gap. | Open |
| 7 | AMBIGUOUS | 03, 03a | The `merge_queue_entry.archived_at` field is described in two slightly different contexts: doc 03 says "archived_at on merge_queue_entry" (set on merge completion) and doc 03a says "archived_at set when the deploy including this entry completes successfully." These are different triggers — one is merge completion, the other is deploy completion. Doc 03a's resolved decision #12 and the DDL comment in doc 03 both reference deploy completion. However, doc 03's prose description says "archived_at on merge_queue_entry" without clearly tying it to deploy completion. The authoritative rule (from doc 03a) is: rows are never hard-deleted, archived_at is set when the deploy including the entry completes. Confirm this is the single correct definition and update doc 03's prose to be unambiguous. | Open |
| 8 | GAP | 05 | The `agent` table has `temp_scope_id` which is described as "the project, task, or session this temp is scoped to" — yet temp_scope_type can also be 'ttl'. When `temp_scope_type = 'ttl'`, what does `temp_scope_id` point to? The spec implies it would be the project the temp belongs to (since all temps are always project-assigned), but this is not explicitly stated. The spec says TTL-scoped temps are "scoped to a time duration" and uses `temp_ttl_seconds` + `temp_expires_at` for the duration. Clarify whether temp_scope_id is always required (pointing to the associated project for ttl-scoped temps) or is nullable for ttl-scoped temps. | Open |
