01 / Core Principles

Foundational design decisions

The project and task domain is built on a set of opinionated principles that shape every interaction.

01

Chat-created, never UI

Tasks are always created through agents or chat. No "new task" buttons. The UI is for viewing, navigating, and reviewing -- not for creation.

02

Every project is a repo

Git is the canonical store for all project files. One repo per project. Main branch is the source of truth, task branches isolate work.

03

Tasks are flat

No parent-child hierarchy between tasks. Large efforts are modeled as multiple tasks connected by dependencies forming a DAG.

04

Explicit flow progression

Agents must signal "step done" to advance. Run completion does not auto-advance. Multiple runs per flow node is normal.

05

Blocked progress creates tasks

There is no separate blocker entity. When progress is blocked, the system creates a task. Notifications can be missed -- tasks persist until resolved.

06

Immutable flow templates

Once a task is using a flow template, it is locked. Changes create new versions. In-progress tasks keep their original flow.

02 / Task State Machine

Work status lifecycle

Eight states govern task progression. The primary path flows from draft through queued, in_progress, review, and into done. Blocked, on_hold, and cancelled serve as auxiliary states. Both done and cancelled are terminal -- if work needs revisiting, create a new task.

Scheduling note

A queued task with unresolved dependencies remains queued but is ineligible for scheduler pickup. Only tasks already in_progress transition to blocked when a new dependency is added mid-execution. The dependency is visible via the dependency table, not via work status.

03 / Flow Templates

Immutable DAGs of work and review

Each task is governed by a flow template -- a directed graph of work and review nodes. The PM designs these conversationally. Review nodes gate quality with approve/reject decisions. Rejection loops create new execution records, preserving full audit history per attempt.

Work Node

Execution by agents

Work nodes are where agents perform tasks. They commit to the task branch, create subtasks if needed, and must explicitly signal "step done" to advance. Multiple runs at a single node is normal -- the agent may need several sessions to complete the work.

Review Node

Quality gate

Review nodes require an explicit approve or reject decision. The reviewer sees a scoped diff: task branch vs the commit_sha from the previous node's execution. Rejection loops create new flow_node_execution records with incremented visit counters.

Immutability rule

Flow templates are immutable once a task is using them. If the flow needs to change, the PM creates a new version. In-progress tasks keep their original flow. New tasks pick up the updated template. This avoids the problem of a flow changing under a task mid-execution.

04 / Subtasks

Scoped to flow node execution

Subtasks are the smallest unit of work, scoped to a specific task and flow node execution. They run sequentially on the task branch to avoid git conflicts. A flow node with subtasks cannot advance until all subtasks are done or cancelled. If a subtask would need its own flow, the parent task is too big and should be split.

Sizing principle

A task is a measurable output with a flow. A subtask is the smallest unit of work within a flow node. Subtasks cannot have their own flows or subtasks. If a subtask would need its own flow, the PM should split the parent task into multiple tasks with dependencies instead.

05 / Merge Queue

Serializing delivery to main

When tasks complete, their branches enter the project merge queue rather than merging immediately. The queue serializes merges in priority-then-FIFO order. Trivial conflicts are auto-resolved; non-trivial conflicts are escalated to the PM. Merge state lives on merge_queue_entry, not on the task itself.

Conflict resolution

Trivial conflicts -- non-overlapping changes to the same file -- are auto-resolved. Non-trivial conflicts are escalated to the PM, who can assign an agent to rebase the task branch. Proactive divergence detection (warning before conflicts materialize) is a future optimization.

06 / Inbox

Action-required queue for humans

The inbox is distinct from notifications. Every item requires a decision and blocks progress somewhere until the human acts. Items persist until acted on -- no expiry, no auto-dismiss. If something sits deferred too long, the PM nudges via chat.

07 / Git Strategy

Every project backed by a repository

Git is the canonical store for all project files -- code, documents, configs, versioned artifacts. This applies whether the project is software, content, or anything else.

One repo per project

Created when the project is created. The PM (or system during setup) initializes it. main is the source of truth.

Task branches

When a task starts execution, a branch is created: task/<slug>. All work happens here. Subtasks share the same branch -- no sub-branches.

Review as diff

Reviewers see task branch vs the commit_sha from the previous node -- each reviewer sees only changes since the last completed step.

08 / Database Schema

12 tables for the project domain

Tasks are flat -- no parent-child between tasks. Subtasks are contained within tasks, scoped to flow nodes. The dependency table is polymorphic. Merge state lives on its own table, not duplicated on the task.
