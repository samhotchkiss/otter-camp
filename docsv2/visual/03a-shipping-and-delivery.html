01 // Delivery Pattern 1

Delivery During Flow

02 // Delivery Pattern 2

03 // Remote Push

Push as Infrastructure

Remote push is infrastructure, not a task. It fires as a merge queue hook after every merge to main. Auto-push retries 3 times with exponential backoff on failure. Subsequent merges still attempt push -- transient issues self-heal.

04 // Pattern 2 Delivery Modes

Three Ways to Ship

For projects using Pattern 2, the PM configures one of three delivery modes. Each determines when and how deploy tasks are created from accumulated merges.

Continuous

auto

Every merge to main triggers a deploy task. If a deploy is already running, the merge is implicitly batched -- when it completes, a follow-up fires if new merges landed. Deploy task creation is protected by a PostgreSQL advisory lock per project to prevent race conditions.

Trigger: merge event on event bus
Best for: internal tools, fast-iteration projects

Gated

manual

Merges accumulate. Human triggers a release via chat with the PM. The PM may proactively suggest deployment when merges pile up. All changes since last deploy ship together.

Trigger: human via chat with PM
Best for: production services, client-facing work

Scheduled

cadence

Deployment runs on a cadence via doc 03's scheduled tasks system. Each deploy picks up all changes since the last deploy. Overlap policy: skip.

Trigger: task schedule (cron-like)
Best for: regular release trains
05 // Environments

Promotion Pipeline

Optional, project-level. An ordered promotion path where each environment tracks its current deployed commit and previous commit (one-level rollback target). No environment branching -- main is the only long-lived branch.

main source of truth
single long-lived branch
-->
staging deployed_commit_sha
previous_commit_sha
deploy_task_id
-->
production deployed_commit_sha
previous_commit_sha
deploy_task_id

Rollback as Deploy Task

Rollback is modeled as a new deploy task targeting the previous commit -- not a state transition. Original tasks stay done. History is append-only.

Step 1 Decision to rollback
-->
Step 2 Create deploy task
target: previous_commit_sha
-->
Step 3 Run deploy flow
possibly emergency fast-path
-->
Step 4 Environment reverted

Original deploy task unmodified. Source tasks stay done. Append-only history.

06 // Database Schema

Two New Tables + Project Columns

Deliberately minimal. Deploy tasks reuse the existing task system. Deploy-specific data lives in task metadata. Two new tables and two new columns on the project table.

project_remote

new table
id uuid pk
project_id uuid fk project
name text unique w/ project
remote_type text git_host | ssh | deploy_platform
url text
push_behavior text auto | manual
auth_config jsonb credential refs
position int push sequence order
metadata jsonb

project_environment

new table
id uuid pk
project_id uuid fk project
name text unique w/ project
position int promotion order
deployed_commit_sha text current commit
previous_commit_sha text rollback target
deployed_at timestamptz
deploy_task_id uuid fk project_task
metadata jsonb

project (additions)

altered table
delivery_mode text continuous | gated | scheduled (null = inherits from project_remote)
deploy_flow_template_id uuid fk flow_template

New Event Types on project_task_event

push_succeeded Recorded on originating task after successful push. Metadata: remote name, URL.
push_failed Recorded on originating task after failed push. Comment: error details. Metadata: remote name, URL, retry count.
deployed Recorded on deploy task after successful deployment. Metadata: environment name, commit SHA.

Merge Queue Entry Retention

merge_queue_entry rows are never hard-deleted. When a deploy completes successfully, the entry's archived_at timestamp is set. Active/pending queries filter to archived_at is null, preserving the full merge audit trail.

07 // Resolved Decisions

18 Decisions, Zero Open Questions

01 Two delivery patterns. Pattern 1: delivery during flow. Pattern 2: delivery after merge.
02 Remote push is infrastructure. Merge queue hook. 3x retry with backoff. Self-healing.
03 Deploy tasks reuse task system. No new entities. Context in task metadata.
04 Three delivery modes. Continuous, gated, scheduled. PM configures.
05 Environments optional, ordered. No branching. main only. Track current + previous SHA.
06 Greenfield projects evolve. Delivery config updates as project matures.
07 Done is truly done. Post-ship issues create new tasks.
08 Rollback is a new deploy task. Not a state transition. Original tasks stay done.
09 Existing event bus. All notifications through existing mechanisms. No new ones.
10 Release notes auto-generated. PM drafts from included tasks. No release entity.
11 Deploy tasks via event handlers. Not by merge queue directly. Clean separation.
12 Continuous mode: implicit skip. No concurrent deploys. Follow-up on completion.
13 Push outcomes as task events. push_succeeded and push_failed on originating task.
14 PM is opinionated about Pattern 1. Proposes delivery nodes for standard project types.
15 Deploy tasks get visual badge. Subtle distinction on task board, not a separate entity.
16 Environment state via deploy completion. Monitoring is separate scheduled task.
17 Gated deploys via chat. Human triggers through PM. PM may suggest proactively.
18 Content delivery edge case noted. Merge conflicts on published content resolved by PM.
