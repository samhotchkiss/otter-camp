Doc 08 -- Deployment and Self-Hosting

One Binary, Three Modes

Same artifact. Configuration determines the deployment.

OtterCamp ships as a single Go binary that runs identically across all environments. Local laptop, remote VPS, or managed multi-tenant -- the mode is determined entirely by configuration, not by building different artifacts. PostgreSQL (with pgvector) is the only required external dependency. Managed mode uses database-per-org isolation -- every org gets its own database, no shared data, no RLS. Everything else has a built-in fallback.

// Deployment Modes

The same binary adapts to three operational profiles. Configuration -- not compilation -- determines behavior.

Mode 1

Local Single-Node

Developers, personal use, evaluation
One process runs everything. API server and Worker share goroutines, a single connection pool, and local filesystem storage. Under a minute to productive.

// Dependency Matrix

PostgreSQL is the only required external dependency. Every other component has a built-in fallback that runs on PostgreSQL or the local filesystem.

Design Constraint

Every additional required service increases the barrier to self-hosting. PostgreSQL is the only thing a self-hoster must provision. The job queue, event bus, and object storage all fall back to PostgreSQL or filesystem -- no Redis, no S3, no message broker required.

// Managed Mode: Database-per-Org

Every organization gets its own PostgreSQL database. The catalog database maps orgs to connections. No shared data, no RLS -- isolation is architectural.

Infrastructure

Catalog Database

A small, shared database that maps tenant identifiers to org database connections. One row per org, cached aggressively, changes infrequently.
  • ContentsOrg slug, DB connection, status
  • UniquenessCross-tenant slug uniqueness
  • CacheIn-memory, short TTL
  • ProvisioningTracks in-progress state
Request Flow

Connection Routing

Every request resolves an org database before any application logic runs. The routing layer is a thin lookup from org slug to database connection.
  • Step 1Extract org from subdomain/URL
  • Step 2Look up in catalog (cached)
  • Step 3Connect to org database
  • PoolingPer-org pools, global ceiling
Per-Org Migration Orchestration

ottercamp migrate --catalog iterates all active tenants and runs pending migrations in parallel (configurable concurrency, default 10). Progress tracked in catalog. Failures are per-org -- one org's failed migration does not block others. New orgs start at the current schema version.

Versioning Policy

PATCH (1.2.3 to 1.2.4): bug fixes, no schema changes, drop-in replacement. MINOR (1.2 to 1.3): new features, additive migrations, backward-compatible. MAJOR (1.x to 2.x): breaking changes, upgrade guide published.

// Security Features

Embedded forward-only migrations, AES-256-GCM encrypted secrets, and a master key architecture that keeps the one critical secret outside the database.

Embedded Migrations

Schema migrations are compiled into the Go binary. Forward-only SQL scripts, numbered sequentially. No rollback migrations -- fixes go forward. Each migration runs in its own transaction. A partial migration is not possible.

Direction Forward-only
Execution Transactional per-migration
Compatibility Backward-compat (minor)
Large tables CONCURRENTLY DDL
Downgrade Refused with error

Encrypted Secrets

All secrets (provider keys, SSH keys, MCP credentials) stored AES-256-GCM encrypted in PostgreSQL. Each secret encrypted with a unique nonce. Decrypted at runtime, held in memory only, never written to disk or logs.

Algorithm AES-256-GCM
Nonce Unique per secret
Storage PostgreSQL (secret table)
Log redaction Pattern-matched
Key rotation Background re-encrypt

Master Key Architecture

The master key is the one secret NOT stored in PostgreSQL. It is sourced from an environment variable, a key file, or cloud KMS. All other secrets are derived from it.

Source 1 OTTERCAMP_MASTER_KEY env
Source 2 Key file path
Source 3 Cloud KMS (managed)
Format 32-byte hex-encoded
Rotation Re-encrypt all + key history

Health Checks

Two endpoints following the liveness/readiness pattern. Non-critical dependencies (model providers, browser, MCP) do not affect readiness.

GET /health Liveness (process up)
GET /ready Readiness (deps OK)
DB check SELECT 1
Storage check list/head bucket
pgvector check SELECT vector('[0]'::vector)
Migration check Schema version match

// TLS Options

Three approaches to TLS for self-hosted deployments. Local mode does not require TLS.

Recommended

Reverse Proxy

Caddy, Nginx, or Traefik in front of OtterCamp. The proxy handles TLS termination, cert renewal, and HTTPS redirects. OtterCamp listens on HTTP internally.
  • ComplexityLow
  • Cert renewalProxy handles
Built-in

ACME / Let's Encrypt

Set TLS_ACME_DOMAIN and OtterCamp handles certificate issuance and renewal automatically. Requires port 443 accessible from the internet.
  • ComplexityLow
  • Cert renewalAutomatic
Manual

Custom Certificates

Set TLS_CERT_FILE and TLS_KEY_FILE to provide your own certs. Renewal is the operator's responsibility.
  • ComplexityMedium
  • Cert renewalManual
