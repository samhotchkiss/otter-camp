Doc 09 -- MCP Integration

Model Context Protocol

Connect agents to external tools, resources, and prompts through a secure, policy-governed MCP client layer — without bloating context windows.

> OtterCamp is always the CLIENT — it consumes, never serves
> Context-aware tool loading — lazy default, eager when declared
01 // Context-Aware Loading

Three Tool Loading Modes

MCP tool schemas are only loaded into agent prompts when needed. No bloat, no wasted tokens, no discovery round-trips for planned work.

Default

Lazy Discovery

Agents see only connection summaries in their prompt. Call mcp.discover to get tool schemas on demand.

  • ~20 tokens per connection in prompt
  • Full schemas loaded only when needed
  • Agent drives discovery as needed
  • Best for open-ended chat sessions
Prompt shows:
github — GitHub repo management
slack — Slack workspace messaging

Agent calls mcp.discover("github") → gets full schemas
~20 tokens/connection
Flow Nodes

Preloading

Flow nodes declare required MCP tools. Schemas are preloaded into the worker's prompt at session start — no discovery needed.

  • Declared in flow_node.mcp_tools
  • Schemas loaded at layer 7 on spin-up
  • Zero round-trip for temp workers
  • PM configures via conversation
flow_node.mcp_tools:
["github.create_pull_request",
 "github.add_labels",
 "github.request_review"]
Only declared tools loaded
Opt-In

Full Toolset

Small connections (<10 tools) can opt in to eager loading. All enabled tool schemas included in every agent prompt.

  • Set eager_load = true on connection
  • All enabled schemas in every prompt
  • Only for small tool sets
  • Admin configures via Frank
"Frank, set the Sentry connection to eager-load its tools."

All 6 Sentry tools appear in every prompt for agents with access.
Use sparingly — watch token cost
Why this matters: A naive MCP integration loads every tool schema into every prompt. 3 connections × 30 tools × ~100 tokens/schema = 9,000 tokens of schemas the agent will never use. Context-aware loading keeps this under control: ~60 tokens for 3 connections by default, plus only the schemas actually needed.

02 // Transports

Two Transport Modes

Every MCP connection uses one of two transport types, set at creation and fixed for the lifetime of the connection.

stdio

Subprocess Transport

OtterCamp spawns the MCP server as a child process and communicates via stdin/stdout. Ideal for local tool servers, language-specific SDKs, and self-hosted environments.

Config: command + args + env + cwd
Secrets injected as environment variables
Sandboxed: restricted filesystem, constrained network, resource limits

HTTP/SSE

Streamable HTTP Transport

OtterCamp connects to a remote HTTP service. Standard HTTP for requests, Server-Sent Events for streaming responses. Best for cloud-hosted and multi-tenant MCP providers.

Config: endpoint URL + headers
Secrets injected as HTTP headers or query params
SSRF protection: requests constrained to registered endpoint only

Circuit Breaker States
Three distinct timeouts: Per-call timeout 30s (how long an MCP call can take), health check timeout 5s (how long a probe can take), circuit breaker recovery 30s (how long before testing a tripped connection). All independent, all configurable per connection.
04 // Classification

MCP Primitive Tiers

MCP exposes three primitive types. OtterCamp classifies each into tiers that determine the policy and execution path.

Tier 2 -- External Mutations

Tools

Callable functions with typed inputs/outputs. External mutations by definition -- every call goes through the full control plane policy path.

  • Capability check: mcp.connection.use
  • Capability check: mcp.tool.invoke
  • Agent profile allow/deny list evaluation
  • Policy result: allow / deny / require_approval
  • Full ToolExecution audit record
  • Input validated against JSON Schema
github.create_issue(title, body, labels)
slack.send_message(channel, text)
Tier 1 -- Read-Only

Resources

Read-only data from the server. No control plane overhead -- handled at the chat layer. Still requires the connection-use capability.

  • Accessed via synthetic read_resource(uri)
  • Requires mcp.connection.use capability
  • Can be cached (default TTL: 5 min)
  • Injectible into agent context as data sources
  • Logged in mcp_execution_log (policy_decision = null)
github.read_resource("repos/otter/schema")
Database schemas, config files, repo listings
Advisory Only

Prompts

Reusable prompt templates from the server. Advisory guidance only -- they do not trigger tool calls or autonomous actions. Skills always take precedence.

  • Cataloged with entry_type = 'prompt'
  • Attachable to flow nodes as supplementary instructions
  • Loaded into agent context at layer 4 (skills)
  • Yield to OtterCamp skills on conflict
  • Server-managed versioning
Code review template, data analysis workflow,
troubleshooting guide
05 // Secrets

Secret Injection Flow

Secrets are stored encrypted, bound by reference, and injected at the transport layer. Agents never see credentials.

1. Encrypted Storage

Secrets (API keys, tokens, OAuth credentials) are stored in the platform's encrypted secret store. Each secret is a named reference, never a raw value.

2. Reference Binding

The mcp_secret_binding table maps connections to their required secrets by named reference. A binding specifies: the logical key (e.g. github_token), the secret reference, and the injection method (header, env_var, query_param, body_field).

3. Runtime Injection

At execution time, the connector runtime resolves the ref:secret_name references from the secret store and injects them into the outgoing request. This happens at the transport layer, after the agent's input has been validated and logged.

INJECTED AFTER LOGGING -- the secret never appears in any log entry or prompt.

4. Response Redaction

If a secret value appears in the MCP server's response (defense in depth), the response sanitizer strips it before the result reaches the agent or is logged.

REDACTED -- any leaked credential is caught and removed.

5. Rotation Without Disruption

Secrets can be rotated in the store without reconfiguring the connection. The binding still points to the same named reference -- only the underlying value changes. Zero downtime credential rotation.

06 // Discovery

Tool Discovery and Enablement

Tools are discovered from the MCP server, cataloged as disabled, and only become available after explicit admin enablement and policy evaluation.

{..}

Discover

Connector runtime calls tools/list on the MCP server. Each tool's name, description, and JSON Schema are fetched and stored in the catalog.

X

Default Deny

All discovered tools are cataloged with is_enabled = false. No tool is available to agents until explicitly enabled.

+

Admin Enables

The admin (via conversation with Frank or the PM) selectively enables tools. "Frank, enable create_issue and list_prs on GitHub."

&

Policy Evaluation

Enabled tools pass through capability checks, agent profile allow/deny, and layered policy. Result: allow, deny, or require_approval.

Catalog refresh happens on connection establishment, manual refresh, and periodic health checks. New tools are always disabled by default. Removed tools are marked status = 'removed' (never deleted) for audit trail integrity. A mcp.catalog.changed domain event notifies the admin of changes.
07 // Schema

Database Schema

Four tables form the MCP data layer. Secrets live in the encrypted store; capability grants live in control plane policy tables.

C

mcp_connection

Connection configuration, transport settings, health state, circuit breaker config, eager load flag. One row per MCP server link.

  • id PK uuid
  • organization_id FK uuid
  • project_id FK uuid? null = org-level
  • name, slug text slug = tool prefix
  • transport_type text stdio | http_sse
  • transport_config jsonb endpoint/cmd+args
  • auth_method text none|api_key|bearer|oauth2|custom
  • status text configuring|active|degraded|disabled|failed
  • eager_load NEW bool default false; preload all tool schemas
  • health_config jsonb interval, timeout, threshold
  • circuit_breaker_config jsonb failure threshold/window/recovery
  • timeout_ms int default 30000
  • retry_config jsonb retries, backoff, write safety
T

mcp_tool_catalog

Discovered tools, resources, and prompts. The system's view of what each MCP server offers. Default-deny enablement. Schemas used by mcp.discover and flow node preloading.

  • id PK uuid
  • connection_id FK uuid
  • entry_type text tool | resource | prompt
  • name text tool identifier
  • description text
  • input_schema jsonb JSON Schema from server
  • is_enabled bool default false
  • status text active | removed
  • resource_uri text? resources only
  • prompt_arguments jsonb? prompts only
L

mcp_execution_log

Full audit trail of every MCP interaction. Inputs and outputs are always secret-redacted. Links to control plane ToolExecution for tier 2 calls.

  • id PK uuid
  • connection_id FK uuid
  • catalog_entry_id FK uuid
  • tool_execution_id FK uuid? tier 2 only
  • agent_id uuid
  • entry_type text tool | resource
  • tool_name text
  • input_params jsonb secrets redacted
  • output jsonb secrets redacted
  • status text success|error|timeout|circuit_open|validation_error
  • policy_decision text? allow|deny|require_approval (null for tier 1)
  • connection_health_at_completion NEW text? health state when call finished
  • duration_ms int
  • retries int default 0
S

mcp_secret_binding

Maps secret references to injection points. The actual secret values live in the encrypted secret store -- this table holds references only.

  • id PK uuid
  • connection_id FK uuid
  • binding_key text logical name (e.g. github_token)
  • secret_ref text reference to encrypted store
  • inject_as text header|query_param|env_var|body_field
  • inject_target text header name, env var, etc.
