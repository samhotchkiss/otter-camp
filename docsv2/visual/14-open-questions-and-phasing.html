Build Roadmap

5 Phases, Foundation to Distribution

Each phase produces a usable product that extends the prior. Dependencies are strict -- nothing in Phase N ships without Phase N-1.

Phase 0
Foundation
Infrastructure only. No user-facing product. Schema, auth, model gateway, event bus, prompt pipeline, control plane, tool framework, bootstrap CLI.
Phase 1
Sync Chat + TUI
First usable product. Human talks to agents via terminal. Chat sessions, starter trio, basic memory, skills, streaming responses.
Phase 2
Projects + Tasks
Autonomous work. Projects as git repos, task flows, subtasks, scheduling, async mode, merge queue, inbox, blocker escalation, shipping.
Phase 3
Self-Building
OtterCamp builds itself. Web UI, MCP integration, system integration (CLI/browser), full control plane, observability, REST API.
Phase 4
Hardening + Distribution
Production ready. Security audit, Docker Compose packaging, mobile UI, multi-tenant with RLS, additional model providers, migration tools.

Name from CLI args or environment variables.

Email/password from CLI args or environment. Assigned as org owner.

Seed model profiles

High-capability (Opus), Standard (Sonnet), Haiku profiles. Requires at least one provider API key.

Four system templates: Single Step, Work+Review, Work+Code Review+Human Review, Research.

7

Frank (Chief of Staff), Lori (Agent Relations), Ellie (Memory). Full profiles, skills, and tool policies.

Product Decisions

Key Resolved Decisions

The three biggest open product decisions from the original stub have all been resolved.

Decision 01
How strong is default human approval for risky actions?
Default-deny for agent capabilities with three policy outcomes and no mid-turn blocking.
  • allow -- execute immediately
  • deny -- return "not permitted" as a tool result, agent adapts
  • draft_review -- stage for human review in inbox, turn continues without blocking

Policy layers are strictly tightening: instance safety > org > project > agent profile. Each layer can only restrict, never expand. No mid-turn approval gates exist -- the turn never blocks waiting for human input.

Decision 02
What is the managed-hosting launch shape vs self-host?
Self-host first (Phases 1-2), managed hosting deferred to Phase 4.

Three deployment modes from one codebase: local single-node, VPS single-tenant (self-host), managed multi-tenant. Docker Compose is the packaging format.

Schema is multi-tenant from day one (every entity carries organization_id), so managed hosting does not require a schema migration. The delta is operational infrastructure, not architecture.

Decision 03
What is the minimum bootstrap dataset?
Starter trio profiles, org session, default skills, model profiles, flow templates, default policies.

Every fresh install is immediately usable. The human opens OtterCamp, talks to Frank, and starts working. No configuration required beyond providing model provider API keys.

Ships with: Frank, Lori, Ellie agents; identity + org default skills; 3 model profiles; 4 flow templates; General session; instance safety + org policy.

Model Profiles
High-Capability

Anthropic Claude Opus. Temp 0.7, tool use enabled, streaming. 60s sync / 120s async timeout. Org default for Frank, Lori, PMs.

Standard

Anthropic Claude Sonnet. Temp 0.7, tool use enabled, streaming. Falls back to high-capability profile. Default for workers and reviewers.

Haiku

Anthropic Claude Haiku. Temp 0.3, tool use disabled, no streaming. 45s timeout. For listening evals, summarization, memory extraction, synthesis.

Flow Templates
Single Step

Work → Done. One work node (role: worker). No review. Simplest possible flow.

Work + Review

Work → Review → Done (reject loops back). Standard for most implementation tasks.

Work + Code Review + Human Review

Work → Code Review → Human Review → Done. For sensitive changes requiring human gate.

Research

Research → Done. Single work node, no review. For exploration and analysis where the deliverable is knowledge.

Policies
Instance Safety

Baked in, not configurable. Cannot delete org, modify system tables, exfiltrate secrets, or bypass auth.

Default Org Policy

Communication tools default to draft_review. CLI/browser/MCP require explicit capability grants. Max 50 tool calls/turn. Max 5min sync / 30min async turns.

Session
General

Org-scoped, sync mode. Participants: human owner, Frank (default_responder), Lori (participant), Ellie (listener). Persistent org-level chat.

Open Questions (~25)

Genuinely unresolved questions collected from across all specs. Organized by domain. Click a category to expand.

Architecture and Infra
4
  • Realtime transport: WebSocket vs SSE for the default realtime channel. SSE is simpler and works through proxies. WebSocket is bidirectional. TUI and web UI may have different preferences.
  • Kubernetes for managed hosting: Is Kubernetes required for managed launch, or can we start with simpler orchestration?
  • Minimum self-host footprint: What are the minimum hardware requirements -- RAM, CPU, disk?
  • API version compatibility: How strict should version compatibility be between self-host and managed cloud?
Auth and Identity
2
  • Password-less auth for self-hosted: Should local single-node deployments support a no-auth mode for developer convenience?
  • Service account keys: Should there be a dedicated service account concept for CI/CD, or are user-scoped API keys sufficient?
Control Plane
3
  • Approval requirements: Should approval requirements be static policy or dynamically risk-scored?
  • Session-wide approval grants: Allow "approve all CLI executions in this session" or only action-by-action?
  • Default capability templates: What minimum set of capabilities ships as defaults for common agent roles?
System Integration
3
  • Browser session isolation: Should browser execution be isolated per task or reusable per session?
  • Minimum sandbox model: Container, namespace, chroot, or process-level sandboxing for CLI execution?
  • Default pre-approval actions: Which system actions require human pre-approval by default vs allow-by-default with capability grant?
MCP
3
  • MCP sampling: Should OtterCamp support the MCP sampling capability where the server requests OtterCamp to make an LLM call on its behalf? Significant trust, cost, and security implications.
  • Connection templates: Ship pre-built templates for popular MCP servers (GitHub, Slack, Postgres) or is conversational setup sufficient?
  • Multi-server tool disambiguation: Beyond connection prefix, should there be routing hints when multiple connections expose similar tools?
Tools
3
  • Tool usage analytics: Should per-agent, per-tool call frequency and success rate be a first-class metric?
  • MCP schema change notification: When an MCP server updates a tool's schema between sessions, how do we communicate the change?
  • Bulk operations: Should batch tools exist (e.g., task.create_batch) for agents that need to create many items?
Security and Observability
3
  • Compliance targets: Which compliance frameworks matter for the first commercial launch -- SOC 2, GDPR, or neither initially?
  • Default retention policy: What default retention period balances usability and privacy?
  • Cost limit behavior: Should cost hard limits fail closed (block all work) or degrade to cheaper models automatically?
Migration
2
  • V1 data imports: Do we offer optional import tools beyond the JSONL memory importer, or keep V2 strictly greenfield?
  • V1 archive retention: How long do we keep V1 archives available internally?
UI
6
  • TUI framework: Bubble Tea confirmed as recommended, but final decision needed.
  • TUI vs CLI relationship: Is the TUI a mode of the existing CLI binary, or a separate binary?
  • Web UI framework: React is recommended but not locked in.
  • Web UI rendering: SSR vs SPA vs hybrid?
  • Mobile platform: iOS first, or iOS and Android simultaneously?
  • Mobile framework: React Native vs native (Swift/Kotlin) vs Flutter?
Risk Assessment

Technically Hardest Challenges

The five areas most likely to require significant iteration and tuning.

Challenge 1
Prompt Assembly Budget Management

The 7-layer pipeline must produce good prompts within tight token budgets across diverse session types (sync org chat, async code task, long-running review). The framework is defined; the real challenge is parameter tuning.

Challenge 2
Memory Retrieval Quality at Scale

V1 proved entity synthesis and taxonomy pre-filtering work at 13K memories. V2 will accumulate much faster across many projects. Retrieval quality at 100K+ memories with complex taxonomy trees is unproven.

Challenge 3
Async Agent Reliability

Agents working autonomously through multi-step flows must handle context limits, tool failures, ambiguous requirements, and environmental surprises. Whether agents can reliably complete multi-hour tasks is the core product risk.

Challenge 4
Git Merge Conflict Resolution

Parallel tasks on separate branches will occasionally conflict. Trivial conflicts are tractable. Non-trivial conflicts require an agent to understand both changes and rebase correctly -- hard for current models.

Challenge 5
MCP Reliability at the Edges

MCP servers with incorrect schemas, flaky behavior, or slow responses produce agent errors hard to diagnose. The agent must be resilient to MCP failures without cascading into bad decisions.

Plan Adjustment Risks

External factors that could force phase delays or architectural changes.

Risk 1
Model Provider API Changes

Provider API changes (rate limits, pricing, deprecations) could force adapter updates. The adapter pattern isolates this, but a major change to the primary provider could delay a phase.

Risk 2
Context Window Economics

The prompt assembly pipeline assumes generous context windows. If model costs increase or context windows shrink, the budget allocation strategy may need rework.

Risk 3
Agent Capability Plateaus

If foundation model capabilities plateau in code generation, long-horizon planning, or tool use accuracy, the product promise weakens. Human review gates are the mitigation.

Risk 4
Self-Host Complexity

PostgreSQL + object storage + model credentials + git repos is meaningful operational overhead. May need a more opinionated deployment (single binary, embedded database).

Risk 5
Memory Cold-Start

On a fresh install, Ellie has no memories, no taxonomy, no entity definitions. Early conversations will have poor memory retrieval until enough data accumulates.
