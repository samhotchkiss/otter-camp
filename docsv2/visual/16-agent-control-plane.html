Architecture

Four-Component Execution Path

Every tier 2 tool call flows through the Execution Broker. The Policy API is the single authority for authorization. Workers are stateless sandboxed executors. Approvals integrate with the inbox and never block the agent's turn.

Policy API

Stateless evaluation engine. Given a principal, capability, scope, and context, returns allow / deny / require_approval. Single authority for authorization.

Cached aggressively. Org/project policies: short TTL. Agent profiles: per-session. Instance safety: compiled at startup.

Execution Broker

Synchronous admission control. The front door. Creates Run records, evaluates policy, dispatches to workers, emits events.

Not a queue -- synchronous admission. Queuing happens at the scheduler and model gateway level.

Worker Runtime

Stateless sandboxed executors. Four domains: internal (DB ops), CLI (containers), browser (isolated contexts), MCP (external calls).

Container-based CLI isolation. Per-run browser contexts. Per-connection MCP capability checks. Resource limits enforced.

Approval Service

Human-in-the-loop via inbox. Pauses runs, creates inbox items, resumes or cancels on human action. Supports session-wide grants.

Non-blocking: returns "queued for review" immediately. Agent's turn continues. No timeout on approvals.

Policy Evaluation

Five Layers, Most-Restrictive-Wins

Policies compose across five layers evaluated highest-priority-first. A deny at any layer is absolute. A lower-priority layer can never grant what a higher-priority layer denies.

1

Instance Safety

Hardcoded. Cannot be overridden. Prevents catastrophic actions: no rm -rf /, no accessing other orgs' data. The "even if everything else is misconfigured, this saves you" layer.

Highest
2

Organization Policy

Set by org owner/admin. Org-wide defaults for capabilities, budget limits, max concurrent runs. Example: "All comms.email.send actions require approval org-wide."

High
3

Project Policy

Set by human or PM for a specific project. Project-specific overrides. Example: "In the billing project, system.cli.execute requires approval."

Medium
4

Agent Profile Policy

The agent's personal capability set, assigned via a template. The base grant that determines what the agent can do before any higher-layer restrictions.

Low
5

Request-Specific Overrides

Applied at runtime based on context. Can only restrict, never expand. Example: agent at 80% daily budget -- expensive capabilities downgrade to require_approval.

Restrict Only

Conflict Resolution

deny At any layer = denied. Period. No lower layer can override.
require_approval At any layer + no deny above = require_approval. Approval requirements accumulate.
allow Only if all applicable layers allow (or are silent). Silence is not denial.
Execution Model

Run Lifecycle

A Run is one end-to-end unit of work. Created by the broker, it captures admission, policy evaluation, execution, and result. Runs decompose into Steps and Attempts.

Data Model

9-Table Schema

Anchored by the run entity. Everything else links back to it. The schema captures the complete execution record: who, what, when, why, and what happened.

run Anchor

One end-to-end unit of work with principal, capability, policy decision, and result.

  • id uuid pk
  • organization_id, project_id, task_id
  • principal_type, principal_id, delegated_by
  • capability, action_type, action_payload
  • policy_decision, policy_decided_by
  • status, failure_reason, failure_class
  • total_input_tokens, estimated_cost_usd
  • idempotency_key, version
run_step

One sequential stage inside a run. Simple actions: 1 step. Compound: multiple.

  • id uuid pk
  • run_id, step_number, name
  • action_type, action_payload
  • status, failure_reason
  • output, output_summary
  • input_tokens, estimated_cost_usd
run_attempt

Retry envelope for a step. Preserves full failure history.

  • id uuid pk
  • run_step_id, attempt_number
  • trigger (initial/retry/approval/manual)
  • status, output, worker_type
  • input_tokens, estimated_cost_usd
model_invocation

Per-LLM-call cost/latency tracking. Links to runs and/or chat turns.

  • id uuid pk
  • run_id, session_id, turn_id
  • provider, model_id
  • input_tokens, output_tokens, cost_usd
  • time_to_first_token_ms, duration_ms
  • purpose, is_retry, is_fallback
tool_execution

Per-tool-call records with policy decisions. Tier 2 calls only.

  • id uuid pk
  • run_id, run_step_id
  • tool_name, tool_tier, tool_domain
  • capability, policy_decision
  • input, output, status
run_artifact

Files, screenshots, logs in object storage. Distinct from chat artifacts.

  • id uuid pk
  • run_id, run_step_id
  • name, artifact_type, content_type
  • size_bytes, storage_path
  • is_primary
run_event

Append-only timeline for replay, debugging, and health monitoring.

  • id uuid pk
  • run_id, run_step_id, sequence
  • event_type (lifecycle/policy/exec/health)
  • event_data, actor_type, actor_id
capability_policy

Declarative policy rules. Capability pattern to decision mapping.

  • id uuid pk
  • organization_id, policy_layer
  • project_id, agent_id
  • capability_pattern, decision, priority
  • conditions, is_active
session_capability_grant

Ephemeral runtime overrides. Session-scoped approval grants.

  • id uuid pk
  • session_id, agent_id, capability
  • granted_by, run_id
  • is_active, granted_at, revoked_at
