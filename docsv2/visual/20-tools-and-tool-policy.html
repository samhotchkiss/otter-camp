01 // Execution Model

Two-Tier Execution

Every tool is assigned a static tier at registration. Tier 1 tools execute directly in the chat layer -- fast and lightweight. Tier 2 tools route through the full control plane -- policy evaluation, broker execution, sandboxing, and RunStep audit trail. Default is tier 2. Tier 1 is a strict whitelist. Migration only goes one direction: tier 1 to tier 2, never the reverse.

Tier 1

Chat-Layer Tools (Read-Only)

How the agent understands its environment. No side effects. Executed directly with a basic scope check.

  • Read-only operations on scoped data
  • No state changes, no external calls
  • Scope check, not policy check
  • Logged as chat_message only
  • 5-second default timeout
  • Parallel execution allowed
22
Tier 1 tools in native catalog
Tier 2

Control-Plane Tools (Mutations)

These change state or reach outside OtterCamp. Full control plane path with policy evaluation and audit trail.

  • Writes, external calls, file modifications
  • Policy: allow / deny
  • Requires matching capability
  • Logged as chat_message + RunStep
  • 10-60s timeouts (tool-dependent)
  • Sequential execution only
~18+
Tier 2 tools (native + all MCP)

Why two tiers? In a typical async turn, an agent does ~30 reads and ~3 writes. Running 30 reads through the full broker pipeline adds substantial overhead for operations that will always be allowed within scope. Reads stay fast; mutations get full rigor.

02 // Tool Taxonomy

Four Tool Categories

Every tool in OtterCamp falls into exactly one of four categories. The category determines where the tool comes from, how it is registered, and what execution path it follows.

1 Native

OtterCamp Native

Ship with OtterCamp. Operate on domain entities -- tasks, projects, flows, memory, sessions, agents.

task.create memory.query flow.advance
Tier 1 (reads) + Tier 2 (mutations)
2 System

System Tools

Filesystem and CLI access within sandboxed workspaces scoped to the project's git repo.

file.read, file.write cli.execute git.commit
Tier 1 (reads) + Tier 2 (writes/CLI)
3 Browser

Browser Tools

Web interaction in isolated browser contexts. Distinct from system tools due to different isolation and risk profile.

browser.navigate browser.click browser.screenshot
Always Tier 2 -- no exceptions
4 MCP

MCP Tools

Dynamically discovered from connected MCP servers. External services outside OtterCamp's control.

mcp:<conn_id>:search mcp:<conn_id>:create (schema from server)
Always Tier 2 -- no exceptions
03 // Tool Resolution

Four-Stage Resolution Pipeline

When an agent takes a turn, the tool set is determined by a four-stage pipeline that runs once at the start of each turn. Each stage narrows the set. The result is cached per session for stability -- tools do not appear or disappear between turns.

1 Universe

Start with all registered tools.

Full native catalog + all active MCP connections in agent's scope. Unhealthy connections excluded.
-->
2 Agent Profile Filter

Allow/deny lists with glob patterns.

project.* | file.write | mcp.* | browser.*
Deny always wins over allow.
-->
3 Flow Node Filter

Soft deprioritization, not hard gate.

Prompt budget optimization. Tools outside declared domains dropped first when budget is tight.
-->
4 Capability Gate

Tier 2 tools require matching capability.

Tier 1 tools bypass this gate. Missing capability = excluded from tool set entirely.
Universe: native catalog + MCP tools
After profile filter: agent-specific subset
After flow node filter: relevant tools prioritized
Final tool set: resolved for this turn

05 // Sensitive Action Handling

Human Review as a Flow Node

Human review is a flow concern, not a policy concern. Policy is strictly binary: allow or deny. When a human needs to review an agent's work (e.g., an email draft before sending), the task flow includes explicit review nodes with human actor type. The tool always does what it says -- draft drafts, send sends. Nothing is secretly intercepted by policy.

Step 1 Agent drafts e.g., email.draft
creates the draft
-->
Step 2 Flow advances Review node activates
(human actor type)
-->
Step 3 Inbox item created Human reviews draft
+ context in inbox
-->
Step 4 Human decides Approve: flow advances
Reject: flow loops back
-->
Step 5 Agent sends email.send executes
at the next flow node

Flow-driven, not policy-driven. The flow graph models the review step explicitly: [email.draft] → [review node, human actor] → [email.send]. The inbox receives items from the flow engine when a review node activates, not from policy interception.

06 // Database Schema

Two Key Tables

tool_definition stores native tool metadata, populated at startup from code. session_tool_set caches the resolved tool set per agent per session for debugging and observability. MCP tools live in mcp_tool_catalog (doc 09).

tool_definition

startup-populated
id uuid pk
name text unique e.g., "task.create"
domain text project | chat | memory | agent | system | browser | communication
category text native | system | browser | communication
tier int 1 = read, 2 = mutation
description text for prompt inclusion
parameter_schema jsonb JSON Schema format
return_schema jsonb optional
required_capability text null for tier 1
is_active boolean feature flags / rollout
version int bumped on schema changes
created_at timestamptz
updated_at timestamptz

session_tool_set

per-session cache
id uuid pk
session_id uuid fk chat_session
agent_id uuid unique w/ session_id
tool_names text[] resolved set, prompt order
tool_versions jsonb {tool_name: version}
mcp_tools jsonb [{conn_id, name, schema_hash}]
resolved_at timestamptz

Observability, not critical path. session_tool_set is for debugging and after-the-fact analysis. The resolved tool set is held in memory during the session. One row per agent per session -- different agents in the same session may have different tool sets.
