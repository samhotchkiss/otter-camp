# Speaker Pipeline Ops Validation Package

## Purpose

This is the canonical next hard validation package after SAM.blog.

The goal is to validate OtterCamp on a mixed operational project instead of another site rebuild. This project should stress:

- research and information gathering
- normalization and scoring/schema design
- structured planning and reporting artifacts
- automation/scripts
- review loops across heterogeneous deliverables

## Project brief

Create a project called `Speaker Pipeline Ops`.

The project should build an operational pipeline for identifying speaking opportunities, scoring them, tracking outreach readiness, and producing a repeatable reporting cadence. OtterCamp should treat this as a real internal operations project with concrete deliverables, not a brainstorming exercise.

## Required outcome areas

OtterCamp should produce a bounded but end-to-end operational package that includes:

- an opportunity sourcing and intake framework
- a scoring model for ranking speaking opportunities
- a schema or structured record format for the pipeline
- an automation plan or lightweight scripts where appropriate
- a reporting/review artifact that shows how the pipeline would be operated over time

## Validation goals

This run should prove that OtterCamp can:

- bootstrap a mixed operational project cleanly without operator coaching
- choose appropriate planning playbooks for non-website work
- decompose research, schema, automation, and reporting work into bounded tasks
- keep parent/orchestration tasks out of primary production work
- survive normal async execution/review/recovery loops
- finish with a clean project state instead of lingering draft shells

## Non-goals

This is not a website redesign.

This is not a pure strategy-doc project with no execution.

This is not a CRM replacement or a fully productionized sales stack. The point is a credible bounded operating system for speaker-pipeline work, not maximum scope.

## Run constraints

- Do not coach OtterCamp into the intended workflow just to make the run succeed.
- Intervene only for true human decisions, broken runtime control, or safety/credential boundaries.
- Any required intervention should become a product fix or a concrete issue, not a normalized operator habit.
- Use the current product defaults and canonical bootstrap path.

## Success criteria

A successful run should satisfy all of the following:

- the project bootstraps cleanly into runnable execution
- the staffed project uses appropriate non-starter delivery roles
- the resulting tasks are bounded and credible
- the project produces concrete artifacts across research, structured planning, and automation/reporting work
- the project finishes without blocked or dangling active work
- final project task state is operationally clean, not merely “good enough”

## Review focus after the run

When reviewing the completed run, focus on:

- whether OtterCamp selected the right work shape for mixed operational work
- whether planning/playbook selection matched the actual task types
- whether task sizing stayed bounded
- whether review/recovery loops were truthful and low-intervention
- whether the final project state matched persisted DB/runtime truth
